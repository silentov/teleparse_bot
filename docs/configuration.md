# Конфигурация проекта

## 1. Как приложение загружает настройки

Точка входа — `get_settings()` в `src/config.py`.

Алгоритм такой:

1. читается `APP_ENV` из переменной окружения;
2. если `APP_ENV` не задан, используется `local`;
3. в `local` режиме приложение требует файл `src/.secrets/.env`;
4. в `prod` режиме приложение пытается найти директорию secrets:
   - `SECRETS_DIR`
   - `/run/secrets`
   - `/var/run/secrets`
5. результат кэшируется через `@lru_cache(maxsize=1)`.

Следствие: после изменения переменных окружения процесс нужно перезапустить.

## 2. Режимы работы

### `APP_ENV=local`

Это основной подтверждённый режим для разработки.

Особенности:

- обязателен файл `src/.secrets/.env`;
- при отсутствии файла старт завершается ошибкой;
- именно этот режим фактически ожидается при локальном запуске `uv run python src/main.py`.

### `APP_ENV=prod`

В коде предусмотрен путь загрузки из директории secrets, но есть важное ограничение:

> Во время аудита не было независимо подтверждено, что текущая схема nested settings корректно и без дополнительной настройки читает все вложенные поля (`app.*`, `redis.*`, `llm.*`) из Docker Secrets в желаемом формате.

Поэтому production-режим в коде **существует**, но перед реальным использованием его нужно проверить отдельным интеграционным тестом на конкретной схеме имён secret-файлов.

## 3. Практически используемые переменные окружения

Проект использует nested-поля формата `SECTION__FIELD`.

### 3.1. Telegram / приложение

| Переменная | Обязательность | По умолчанию | Комментарий |
|---|---|---|---|
| `APP__API_ID` | обязательно | нет | Telegram API ID; в `main.py` приводится к `int` |
| `APP__API_HASH` | обязательно | нет | Telegram API hash |
| `APP__TOKEN` | обязательно | нет | bot token |
| `APP__NAME` | опционально | `Граппер` | в текущем runtime почти не используется |

### 3.2. Redis

| Переменная | Обязательность | По умолчанию | Комментарий |
|---|---|---|---|
| `REDIS__HOST` | опционально | `localhost` | используется при сборке URL |
| `REDIS__PORT` | опционально | `6379` | валидируется как диапазон `1..65535` |
| `REDIS__DB` | опционально | `0` | должен быть `>= 0` |
| `REDIS__USERNAME` | опционально | `None` | полезно при ACL |
| `REDIS__PASSWORD` | опционально | `None` | практически нужен при использовании `redis.conf` из репозитория |
| `REDIS__URL` | опционально | нет | если не задан, собирается из полей выше |
| `REDIS__MAX_CONNECTIONS` | опционально | `20` | пул соединений |
| `REDIS__SOCKET_CONNECT_TIMEOUT` | опционально | `5.0` | таймаут подключения |
| `REDIS__SOCKET_TIMEOUT` | опционально | `5.0` | таймаут операций |
| `REDIS__HEALTH_CHECK_INTERVAL` | опционально | `30` | период healthcheck соединения |
| `REDIS__DECODE_RESPONSES` | опционально | `True` | строки вместо bytes |
| `REDIS__TTL_SECOND` | опционально | `1800` | TTL FSM-контекста |

### 3.3. LLM

| Переменная | Обязательность | По умолчанию | Комментарий |
|---|---|---|---|
| `LLM__MODEL` | обязательно для полезной работы | пусто | имя модели |
| `LLM__API_KEY` | обязательно для полезной работы | пусто | ключ провайдера |
| `LLM__SYSTEM_PROMPT` | фактически обязательно | пусто | system prompt для суммаризации |
| `LLM__TEMPERATURE` | опционально | `1.0` | валидируется как `>= 0` |
| `LLM__TIMEOUT` | опционально | `30` | таймаут LLM-вызова |
| `LLM__MAX_RETRIES` | опционально | `0` | количество повторов на уровне model client |
| `LLM__TOKENS` | опционально | `8000` | **сейчас не используется кодом** |
| `LLM__API_URL` | опционально | `None` | **сейчас не передаётся в `init_chat_model`** |

## 4. Что реально логируется при старте

После загрузки настроек приложение пишет в лог `settings.safe_dump()`.

Особенности:

- секреты маскируются;
- пароль Redis не выводится открыто;
- часть параметров, которые есть в модели, может не попасть в лог намеренно.

## 5. Redis URL: как он формируется

Если `REDIS__URL` не задан, код собирает его сам:

- с `username + password`, если заданы оба;
- с `password`, если username нет;
- без auth-части, если credentials отсутствуют.

Это удобно для локальной разработки, когда проще задавать `HOST/PORT/DB` отдельно.

## 6. Локальная конфигурация против Docker Compose

Во время аудита зафиксировано важное расхождение:

- `docker-compose.yaml` прокидывает **корневой** `.env`;
- код локального режима требует `src/.secrets/.env`.

Это означает, что текущий `docker-compose.yaml` **нельзя считать полностью синхронизированным** с приложением в режиме `local`.

Практический вывод:

- для локальной разработки безопаснее запускать только Redis через Compose;
- полный containerized startup требует дополнительной настройки конфигурации.

## 7. Production-секреты: что можно и чего нельзя утверждать

Можно утверждать по коду:

- приложение умеет искать директорию secrets;
- путь можно переопределить через `SECRETS_DIR`;
- `BaseSettings` создаётся с `_secrets_dir`.

Нельзя уверенно утверждать без отдельного теста:

- какой именно flat/nested naming secrets-файлов гарантированно сработает для `app.api_id`, `redis.password`, `llm.api_key`;
- что текущая production-конфигурация полностью готова к Docker Secrets без дополнительного `settings_customise_sources()`.

Именно поэтому production-конфигурация в документации отмечена как **частично подготовленная, но не до конца подтверждённая runtime-проверкой**.
