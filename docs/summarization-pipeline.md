# Пайплайн суммаризации

## 1. Что делает пайплайн сейчас

На текущем этапе проект использует **простую одноступенчатую схему**:

1. userbot получает последние `N` сообщений канала;
2. каждое сообщение преобразуется в DTO с полями `id` и `text`;
3. список DTO отправляется в `LLMProvider`;
4. `LLMProvider` делает один запрос к chat model;
5. бот показывает пользователю итоговую сводку.

Это важно: сейчас нет промежуточных стадий вроде чанкинга, кластеризации тем, map-reduce summary или отдельного post-processing.

## 2. Нормализация сообщений

В `UserBot.get_messages()` каждое сообщение Telegram преобразуется так:

```python
TelegramMessageDTO(id=msg.id, text=(msg.message or ""))
```

Практические последствия:

- в LLM попадает только `msg.message`;
- автор, дата, тип вложения, ссылки на медиа и grouped media отдельно не нормализуются;
- media-only сообщение может превратиться в пустую строку;
- качество summary напрямую зависит от того, насколько текстово представлены исходные посты.

## 3. Формирование LLM-входа

`LLMProvider._prepare_message()` строит `HumanMessage`, где каждый элемент выглядит как текстовый блок:

```text
[id=<message_id>] <message_text>
```

Это означает:

- идентификатор сообщения сохраняется в prompt;
- отдельной структуры по времени, источнику или типу контента нет;
- модель получает один плоский список сообщений.

## 4. Как создаётся модель

Сейчас используется `langchain.chat_models.init_chat_model(...)` с параметрами из `config.llm`.

Через Context7 подтверждено, что:

- `init_chat_model` — стандартный путь инициализации chat model в LangChain;
- `with_structured_output(...)` применяется для принуждения модели к структурированному формату ответа;
- `ainvoke(...)` — штатный асинхронный способ вызова модели.

## 5. Structured output

Модель оборачивается в:

```python
structured_model = self._model.with_structured_output(StructuredMessage)
```

Схема `StructuredMessage` ожидает:

- `model_message: str`
- `urls: list[str]`

После ответа провайдер:

- принимает Pydantic-модель, dict или объект с `model_dump()`;
- валидирует структуру;
- возвращает `LLMSummaryResult`.

## 6. Что пользователь видит в результате

UI-форматирование происходит в `bot/texts/editable.py`.

Пользователь получает:

- имя канала;
- список идентификаторов сообщений в виде `channel/id`;
- текст `summary.model_message`.

Поле `urls`, которое возвращает LLM, в текущем пользовательском сообщении **не используется**.

## 7. Ограничения текущей реализации

### 7.1. Нет token budgeting

В конфигурации есть `LLM__TOKENS`, но текущий код его не использует.

Следствие:

- риск переполнения контекста модели при больших выборках;
- отсутствует адаптивное уменьшение объёма входных данных;
- нет защиты от слишком длинных отдельных постов.

### 7.2. Нет чанкинга и многоступенчатой суммаризации

Сейчас отсутствуют:

- разбиение больших пакетов сообщений на чанки;
- группировка по темам;
- промежуточные summary по частям;
- финальная synthesis-стадия.

Для большого или смешанного контента это архитектурное ограничение.

### 7.3. Нет специальной обработки media-only контента

Если канал публикует:

- фото без текста;
- видео без подписи;
- документы без текстового описания,

то LLM почти не получает полезного содержания.

### 7.4. Нет нормализации ссылок и вложений

Сейчас в summary-пайплайн не включаются:

- permalink сообщения в формате `https://t.me/...`;
- metadata по вложениям;
- признаки grouped media.

## 8. Что учитывать при развитии пайплайна

Если расширять этот слой, безопасное направление такое:

1. нормализовать сообщения богаче, чем просто `id + text`;
2. ввести token budget до LLM-вызова;
3. отделить обработку коротких и длинных батчей;
4. отдельно обрабатывать media-only посты;
5. не смешивать Telegram UI-логику с LLM-логикой в `MainBot`.
