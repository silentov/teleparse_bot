# Разработка и внесение изменений

## 1. Рабочая модель проекта

Сейчас проект лучше воспринимать как четыре слоя:

- `bot/` — Telegram UI и orchestration;
- `fsm/` — пользовательское состояние и маршрутизация;
- `infrastructure/redis/` — доступ к Redis и локации ключей;
- `llm/` — интеграция с моделью и контракты результата.

Если вносите изменения, важно не смешивать эти роли.

## 2. Базовые команды разработчика

Установка зависимостей:

```bash
uv sync
```

Запуск приложения:

```bash
uv run python src/main.py
```

Проверка линтером:

```bash
uv run ruff check .
```

## 3. Что важно сохранять при изменениях

### Асинхронность

- не добавляйте блокирующий I/O в event loop;
- не делайте неограниченный fan-out запросов;
- учитывайте таймауты и отмену задач.

### Границы слоёв

- не переносите LLM-логику в Redis-слой;
- не тащите прямую работу с Telethon в модули хранения;
- не храните в FSM лишние данные, которые не нужны для UX-сценария.

### Документация

- если меняется runtime, конфиг, архитектура или developer workflow — обновляйте docs в том же цикле изменений;
- source of truth — код и конфиги, а не старые заметки.

## 4. Known issues и технический долг

Ниже перечислены не все возможные улучшения, а именно наблюдения, подтверждённые аудитом.

### 4.1. Docker / config mismatch

`docker-compose.yaml` и загрузчик настроек приложения сейчас описывают разные ожидания по местоположению env/secrets.

Практическое следствие: контейнерный запуск всего приложения нужно отдельно выравнивать и проверять.

### 4.2. Production secrets не доведены до подтверждённого состояния

Код для `_secrets_dir` есть, но runtime-совместимость nested secrets layout не подтверждена отдельным интеграционным сценарием.

### 4.3. `WAIT_PARSE_START` не используется

Состояние есть в enum, но в живом сценарии не задействовано.

### 4.4. Есть мёртвая/неиспользуемая ветка API локов

`LockService.user_action()` обращается к `RedisKeys.lock_user_action()`, которого нет в `RedisKeys`.

Сейчас это не ломает runtime только потому, что путь не используется.

### 4.5. Не все конфигурационные поля реально участвуют в runtime

Сейчас объявлены, но не используются напрямую:

- `LLM__TOKENS`
- `LLM__API_URL`

Их нельзя считать рабочими runtime-функциями только по факту наличия в модели настроек.

### 4.6. `orjson` используется в коде напрямую

Redis-сервис сериализует данные через `orjson`. Во время аудита библиотека присутствовала в окружении и lock-файле, но отдельного явного упоминания в `pyproject.toml` нет.

Если будете трогать dependency management, эту зависимость нужно проверить отдельно.

## 5. Безопасное направление дальнейшего развития

Если развивать проект дальше, наиболее логичный порядок такой:

1. выровнять container/runtime-конфигурацию;
2. закрыть неопределённость вокруг production secrets;
3. улучшить summarization pipeline:
   - token budget,
   - chunking,
   - mixed-topic handling,
   - media-only handling;
4. добавить тесты на FSM, dispatcher и конфигурацию;
5. добавить операционные safeguards для Telegram rate limits и flood wait.
