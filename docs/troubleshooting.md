# Troubleshooting

## 1. Ошибка `Local env file not found`

### Симптом

Приложение падает на старте с ошибкой вида:

```text
ConfigurationError: Local env file not found: .../src/.secrets/.env
```

### Причина

`APP_ENV=local` — режим по умолчанию, а в нём код жёстко требует `src/.secrets/.env`.

### Что делать

1. создайте `src/.secrets/.env`;
2. заполните обязательные переменные;
3. перезапустите процесс.

## 2. Бот не подключается к Redis

### Симптом

- старт останавливается на `Redis ping`;
- в логах ошибки подключения или auth.

### Что проверить

1. Redis действительно запущен:

```bash
docker compose up -d cache
```

2. параметры совпадают с конфигом приложения:

- `REDIS__HOST`
- `REDIS__PORT`
- `REDIS__USERNAME`
- `REDIS__PASSWORD`

3. если используете `redis.conf` из репозитория, дефолтный пользователь для приложения — `fsm`.

### Быстрая проверка

```bash
docker compose exec cache redis-cli --user fsm -a FsmPass8989 ping
```

Если вы изменили пароль в `redis.conf`, команда должна использовать ваш актуальный пароль.

## 3. UserBot каждый раз просит авторизацию заново

### Симптом

При каждом запуске снова требуется номер телефона и код.

### Причина

Session-файлы не сохраняются или процесс запускается из другой рабочей директории.

### Что делать

1. запускайте приложение из корня репозитория;
2. проверьте наличие файлов `bot_session.session` и `async_session.session`;
3. убедитесь, что они не удаляются между запусками;
4. для контейнеров заранее продумайте, как будут монтироваться session-файлы.

## 4. Ошибка доступа к Telegram-каналу

### Симптом

Пользователь получает ошибку вида:

```text
Не удалось получить сообщения канала '...'
```

### Возможные причины

- username введён с ошибкой;
- канал не публичный;
- userbot-аккаунт не имеет доступа к каналу;
- Telegram вернул `RPCError`.

### Что делать

1. проверьте username без `https://t.me/`;
2. убедитесь, что канал открывается в аккаунте userbot;
3. повторите запрос позже, если проблема похожа на Telegram-side сбой.

## 5. LLM вернул пустой или невалидный ответ

### Симптом

- `LLMEmptyResponseError`
- `LLMProviderError`
- пользователь получает сообщение об ошибке вместо summary.

### Что проверить

1. валиден ли `LLM__API_KEY`;
2. корректно ли указана `LLM__MODEL`;
3. не пустой ли `LLM__SYSTEM_PROMPT`;
4. не слишком ли большой объём сообщений вы отправили в модель.

### Важный нюанс

Structured output требует, чтобы модель вернула объект, совместимый со схемой `StructuredMessage`. Если модель начинает отвечать свободным текстом, валидация упадёт.

## 6. Docker Compose поднимает Redis, но bot service не стартует как ожидалось

### Причина

Во время аудита зафиксировано расхождение:

- compose использует корневой `.env`;
- приложение в local-режиме ищет `src/.secrets/.env`.

### Практический вывод

Сейчас Compose надёжнее использовать как способ поднять Redis, а не как полностью подтверждённую end-to-end среду для приложения.

## 7. Пользователь «застрял» в состоянии FSM

### Симптом

- кнопки и ввод перестали вести к ожидаемому сценарию;
- старые данные контекста мешают новой сессии.

### Что происходит

FSM хранится в Redis с TTL 30 минут. Если контекст не был корректно сброшен, он может временно влиять на поведение.

### Что делать

1. попросите пользователя отправить `/start`;
2. при необходимости удалите ключ FSM вручную;
3. проверьте, нет ли параллельных событий на этого же пользователя.

Формат ключа:

```text
fsm:<chat_id>:<user_id>
```

## 8. Где смотреть логи при разборе инцидента

- локально: `src/logs/app.log` и `src/logs/error.log`;
- в Docker: `docker compose logs -f cache` для Redis;
- stdout/stderr процесса приложения — основной источник информации о старте и исключениях.
